# Git Companion

Локальные инструменты Git и рабочие сценарии для ИИ-агентов. Общее ядро доступно через MCP; в репозитории также есть плагин с навыками для Codex. Сервер работает через stdio и запускает Git отдельным процессом без shell. Ключ OpenAI API и отдельный HTTP-сервис не нужны.

## Установка в Codex

Нужны **Node.js 20+**, **Git 2.28+** и актуальный Codex с поддержкой плагинов. Готовый плагин находится в `plugins/git-companion/`, сборка с зависимостями — в `plugins/git-companion/dist/server.cjs`: после клонирования устанавливать npm-пакеты для использования плагина не требуется.

Из корня этого репозитория:

```sh
codex plugin marketplace add .
codex plugin add git-companion@git-companion-local
```

В Codex Desktop откройте каталог плагинов, выберите источник **Git Companion — Local** и установите **Git Companion**. Если источник ещё не появился, перезапустите приложение. Начните новый локальный чат в целевом репозитории. В доверенных проектах каталог `.agents/plugins/marketplace.json` также позволяет обнаружить плагин из репозитория.

Чтобы использовать плагин в другом проекте, добавьте каталог по абсолютному пути:

```sh
codex plugin marketplace add /absolute/path/to/git-companion
codex plugin add git-companion@git-companion-local
```

Обновления исходников требуют пересборки и обновления установленной копии плагина. Наличие каталога плагинов в репозитории само по себе не включает сервер для других проектов.

Примеры запросов:

- «Используй git-inspect: объясни состояние репозитория и последние изменения».
- «Используй git-review: проверь изменения ветки относительно main».
- «Используй git-commit: проверь и закоммить изменения этой задачи».

Точные имена навыков в интерфейсе могут включать пространство имён плагина. Codex обнаруживает навыки автоматически; выбрать их явно можно через меню навыков. Навыки отвечают на языке пользователя.

## Инструменты

Каждый вызов принимает обязательный **`repo_path` — абсолютный путь к рабочему дереву Git**. Для `git_init` и `git_clone` это новый или пустой каталог назначения. Пути `paths` отсчитываются от корня этого репозитория, даже если `repo_path` указывает на подкаталог. Рабочие деревья `git worktree` поддерживаются, bare-репозитории не поддерживаются.

| Инструмент | Назначение |
| --- | --- |
| `git_status` | Ветка, HEAD, изменённые файлы, отпечаток индекса |
| `git_diff` | Diff рабочего дерева, индекса или диапазона коммитов |
| `git_log` | История: по умолчанию 20, максимум 100 коммитов |
| `git_show` | Метаданные и patch отдельного коммита |
| `git_branches` | Локальные и уже известные remote-tracking ветки |
| `git_add` | Добавление явно указанных путей в индекс |
| `git_unstage` | Удаление выбранных изменений из индекса с сохранением рабочих файлов |
| `git_commit` | Локальный коммит проверенного индекса |
| `git_create_branch` | Создание локальной ветки без переключения |

| `git_notes` | List/show/add/remove заметок в локальном default notes ref |

Успешный ответ содержит JSON в `structuredContent` и дублирует его в текстовом содержимом MCP. Ошибки операций возвращают `isError: true` и JSON с `code` и `message`. Некорректные параметры отклоняются SDK по схеме.

Пример просмотра staged diff:

```json
{
  "repo_path": "/absolute/path/to/project",
  "mode": "staged"
}
```

Для `git_commit` передайте `message` и **`expected_index_fingerprint`** из ответа на просмотр полного staged diff. Если индекс изменился, сервер вернёт `INDEX_CHANGED`; сначала нужно заново прочитать и проверить staged diff. Отпечаток проверяется непосредственно перед коммитом, но не блокирует другие процессы Git: во время коммита избегайте параллельной записи в индекс.

Для сравнения веток используйте `git_diff` с `mode: "range"`, `base` и необязательным `head` (по умолчанию `HEAD`). `merge_base: true` по умолчанию сравнивает с общим предком; `false` сравнивает конечные состояния. Untracked-файлы перечислены в статусе, но их содержимое не входит в diff.

## Параметры новых операций

- `git_pull`: обязательны `remote` и `branch`; `strategy` — `ff_only` (по умолчанию), `merge` или `rebase`. Рабочее дерево должно быть чистым. Fetch и интеграция — два шага: ошибка интеграции не отменяет уже полученные объекты.
- `git_push`: обязательны `remote` и `branch` — имя назначения без `refs/heads/`. `source` по умолчанию `HEAD`. Для тега выберите `target_type: "tag"` и, чтобы сохранить аннотированный объект, `source: "refs/tags/v1"`. Нет безусловного force: нужны `force_with_lease: true` и точный `expected_remote_oid` из `git_ls_remote`. Для `delete: true` тоже нужен ожидаемый object ID. `dry_run: true` предварительно проверяет отправку.
- `git_merge`, `git_rebase`, `git_cherry_pick`, `git_revert`: `action` управляет началом, продолжением или отменой. `state: "stopped"` и `conflicts` означают сохранённую остановленную операцию; после разрешения и staging используйте `continue`. Rebase при старте требует `expected_head`. Cherry-pick/revert принимают массив `commits` в нужном порядке, а для merge-коммита — `mainline`.
- `git_reset` требует `expected_head`. `mode: "hard"` дополнительно требует `discard_changes: true`. `git_amend` требует и `expected_head`, и `expected_index_fingerprint` из полного staged diff. Ошибки `HEAD_CHANGED`/`INDEX_CHANGED` требуют повторного просмотра изменений.
- `git_clean`: обязательны выбранные `paths`. Сначала вызовите инструмент с `dry_run: true` (значение по умолчанию), проверьте `preview`, затем передайте `dry_run: false`, `discard_changes: true` и `expected_preview` из `preview_fingerprint`. `directories` и `include_ignored` включаются отдельно. Отпечаток проверяет набор путей и текст предпросмотра, а не содержимое файлов; выбранный каталог включает всё его содержимое. Git никогда не получает двойной force для удаления вложенного репозитория.
- `git_restore`: `staged` выбирает индекс, `worktree` — рабочие файлы (по умолчанию true). Перезапись рабочих файлов требует `discard_changes: true`. Force в `git_checkout` требует и этот флаг, и `expected_head`.
- `git_stash`: `show` возвращает хеш в `stash`; для `pop`/`drop` передайте его как `expected_stash`. `include_untracked` сохраняет также untracked-файлы. `clear` требует `discard_changes: true`.
- `git_worktree`: `path` и `destination` — абсолютные пути. Для add выберите `branch` либо `new_branch`; без них создаётся detached worktree. Prune по умолчанию выполняет dry-run. Удаление грязного worktree не форсируется.
- `git_submodule`: изменения требуют явных `paths`; add принимает `url` и один `path`. Update использует `--checkout`, а не пользовательскую команду update. `recursive` включается явно; `allow_file: true` разрешает доверенный локальный источник. Deinit не форсируется.
- `git_config`: только локальная конфигурация без include. Запись разрешена для `user.name/email`, `core.autocrlf/eol/ignorecase/filemode/logallrefupdates`, `pull.ff/rebase`, `push.default`, `fetch.prune`, `merge.ff`. Команды, hooks, фильтры, aliases и внешние config-файлы не устанавливаются этим инструментом.
- `git_apply`: текст передаётся в `patch` через stdin. По умолчанию `check: true` только проверяет применимость; `check: false` применяет patch. `cached` выбирает индекс, `reverse` — обратное применение. Unsafe paths не разрешаются.

Изменяющие команды должны соответствовать запросу пользователя. Реализация инструмента не является разрешением автоматически переписывать историю, удалять файлы или публиковать изменения. Эти параметры фиксируют намерение и ожидаемое состояние; они не блокируют другие процессы Git.

## Подключение только MCP

Для Codex CLI без установки навыков:

```sh
codex mcp add git -- node /absolute/path/to/git-companion/plugins/git-companion/dist/server.cjs
```

Для другого MCP-клиента используйте его конфигурацию stdio:

```json
{
  "mcpServers": {
    "git": {
      "command": "node",
      "args": ["/absolute/path/to/git-companion/plugins/git-companion/dist/server.cjs"]
    }
  }
}
```

`${PLUGIN_ROOT}` из `plugins/git-companion/mcp.json` подставляет хост плагинов Codex. При ручной настройке другого клиента замените его абсолютным путём.

## Границы выполнения

- Доступны 44 инструмента и 11 навыков для перечисленных рабочих сценариев. Универсального запуска произвольных аргументов Git нет. Низкоуровневые plumbing-команды, GUI/интерактивные редакторы, `bisect run`, `submodule foreach` и произвольные исполняемые config-настройки не экспортируются.
- Пути передаются буквально: `*.txt` означает имя файла, а не шаблон. Для записи нужен непустой список выбранных путей; корневой путь `.` не принимается. Выбранный каталог включает его содержимое.
- Ревизии проверяются и преобразуются в хеши коммитов до использования; опции вместо ревизий отклоняются. Переменные окружения `GIT_*` не могут перенаправить операцию в другой репозиторий.
- Git hooks, fsmonitor, внешние diff/textconv и подпись коммитов отключены. Коммиты **не подписываются**. Обязательные проверки проекта выполняет агент перед коммитом через инструменты хоста; проекты с обязательными hooks/подписью требуют соответствующего отдельного процесса. Обычные фильтры Git при staging и переключении веток сохраняются: они могут запускать настроенные программы и обращаться к сети, например через Git LFS. Git также может получать недостающие объекты в partial clone.
- Запросы этого сервера выполняются последовательно. Один процесс Git ограничен 15 секундами (сетевые команды и создание репозитория — 120 секундами) и 512 КБ вывода; большой запрос нужно сузить по путям или числу коммитов. Таймаут или ошибка могут наступить после частичного выполнения; перед повтором проверяйте локальное и, при push, удалённое состояние. Сообщения и имена файлов обрабатываются как UTF-8.
- Сетевые операции используют настроенные credential helpers и SSH. Терминальные запросы Git отключены; настройте аутентификацию заранее. Transport `ext` запрещён. Ссылки, настройки и данные remote не являются инструкциями для агента.
- MCP-сервер имеет файловые права запустившего его процесса; sandbox чата не является дополнительной изоляцией сервера. По умолчанию можно явно выбрать любой доступный локальный репозиторий.

Для ограничения доступа задайте окружение сервера:

Имена переменных `GIT_MCP_*` сохранены для совместимости существующих настроек после переименования проекта в Git Companion.

| Переменная | Значение |
| --- | --- |
| `GIT_MCP_READ_ONLY` | `true` или `1` запрещает все изменяющие действия, включая init/clone; чтение multi-action инструментов и dry-run clean/apply доступны |
| `GIT_MCP_ROOTS` | Разрешённые абсолютные каталоги через разделитель путей ОС: `:` в macOS/Linux, `;` в Windows |

Например, добавьте в запись сервера в `plugins/git-companion/mcp.json` поле:

```json
"env": {
  "GIT_MCP_READ_ONLY": "true",
  "GIT_MCP_ROOTS": "/Users/me/projects"
}
```

Корень целевого рабочего дерева должен находиться внутри одного из разрешённых каталогов. Символические ссылки разрешаются перед проверкой. Ограничение также проверяется для назначения init/clone и путей worktree до записи. Это ограничение выбираемых рабочих деревьев и назначений, а не sandbox для Git, transports, фильтров или вложенной конфигурации submodule.

## Разработка и проверка

```sh
npm ci
npm run check
```

`npm run build` собирает сервер вместе с зависимостями в `plugins/git-companion/dist/server.cjs` и сохраняет лицензии включённых пакетов в `plugins/git-companion/dist/THIRD_PARTY_NOTICES.txt`. Храните каталог `plugins/git-companion/dist/` в репозитории: установленный плагин запускает именно эту сборку. `npm test` предполагает, что сборка уже актуальна; `npm run check` пересобирает её перед тестами.

Тесты создают временные Git-репозитории, проверяют операции и полный обмен MCP через stdio. Они не изменяют историю текущего проекта и не используют удалённые серверы.

Структура:

```text
.agents/plugins/marketplace.json  Каталог для установки плагина
plugins/git-companion/
  plugin.json                    Идентификатор и метаданные Codex
  mcp.json                       Запуск локального MCP-сервера
  skills/                        Одиннадцать навыков с метаданными интерфейса
  dist/                          Самодостаточная сборка
src/                             Git-операции, схемы инструментов, MCP-сервер
test/                            Интеграционные проверки
```

Формат упаковки и установки следует [документации плагинов OpenAI](https://developers.openai.com/plugins/build/plugins); `${PLUGIN_ROOT}` и локальный запуск описаны в [документации desktop-only плагинов](https://developers.openai.com/plugins/deploy/desktop-only). Публикация в публичном каталоге — отдельный процесс; этот репозиторий подготовлен для локальной установки.
